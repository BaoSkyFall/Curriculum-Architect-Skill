# Curriculum Design Reference

## Design Sequence

Use this order unless evidence supports a change:

```text
Audience -> outcome -> concept -> mental model -> practice -> integration -> assessment
```

Each module should answer:

- Why does this exist in the course?
- What must students already understand?
- What can students explain or build afterward?
- Which capstone artifact does it advance?

## Dependency Rules

Record prerequisites explicitly. Basic software flow precedes frontend/backend boundaries; HTTP and JSON precede API debugging; persistence precedes data pipelines; LLM calls precede retrieval-augmented generation.

Dependencies are hypotheses, not sacred ordering. Split or merge modules when the learner journey becomes clearer.

## Quality Signals

Prefer observable outcomes, small labs, visible outputs, and assessment prompts that ask students to explain system behavior. Flag duplicate concepts, unexplained jumps, tool-first lessons, and labs that do not serve the capstone.
